## What was fixed in this session

### 1. Space opened the File menu (craft-libs)

`KeyUse::of(Input::Pointer)` defaulted to `ActivateKeys::Both`, so every pointer control activated on
Space, and `route.rs` turned a bare Space press into `PressRoute::Activate`. The menu bar's File button
is such a control. Fixed in commits `f7fc484a` (egui's own Space→click) and `8fbb0720` (the default is
`Enter`, `route.rs` leaves a bare Space to `PressRoute::Free`, eight components ask for `Enter`).

### 2. A menu bar click aborted the process (craft-libs, the "Filter" crash)

`accesskit_consumer`'s `Node::controls()` unwraps every id (`node.rs:999`); the runtime published a
`controls` relation naming a node the same update did not carry, so the UIA adapter killed the app.
Fixed in `e875a7c9`: `access.rs` drops dangling relations, `plugin.rs` installs the `output_hook`.
Two tests cover it. **The owner has not confirmed this one on his machine.**

### 3. The tab's × closed the wrong document (PhotoCraft)

`crates/ui-egui/src/canvas/tabs.rs` passed a `DocId` (a counter that starts at 1) where `file.close`
expects an **index**, and the error was swallowed by `let _ =`. With one document index 1 is out of
range, so nothing happened; with two, index 1 is the *second* document, so the right tab closed when
the left × was clicked. Fixed in `7588a8e3fc`: the index is looked up, the failure goes to the status
line, and the tab context menu's Close / Close Others rows take the index too. Test:
`the_close_button_on_a_tab_closes_its_document` (fails without the fix, measured).

### 4. A save could be reported as failed after it had been written (PhotoCraft)

`ERROR_ACCESS_DENIED` (5) from the directory flush made the save fail even though the bytes were
already renamed into place, so the document stayed unsaved and its recovery data was discarded. Five
tests failed on it (JPEG copy, PDF print, Save for Web, custom paper, smart-object link write).

Measured before changing anything: a **file** opened for writing flushes fine; a **directory** handle
answers 5 whatever access it asks for (`FILE_ADD_FILE`, `GENERIC_WRITE`, read+write), while the same
`FlushFileBuffers` from a non-Rust process on the same folder succeeds. So 5 says the flush could not
be asked for, not that the write was lost. `dir_sync_unsupported` now counts 5 as flushed on Windows
(`ERROR_IO_DEVICE` 1117 and the rest still fail), and the two guard tests that pinned 5 as a failure
were updated with that reason (`atomic/tests.rs`, `store/durability_tests.rs`). Commit `2780a50e4f`.

### 5. The print dialog lost its remembered printer (PhotoCraft + craft-libs)

`open_print` skipped printer / copies / duplex / grayscale when copying the remembered print and never
called `write_settings`, so the panel opened with no printer. `craft_print::State::poll` also replaced
the remembered printer with an empty name whenever discovery came back empty — an empty list says the
spooler could not be asked, not that the printer is gone. Both fixed (`2780a50e4f`, craft-libs
`0450311d`).

### 6. LaMa Cleaner stopped working

The engine command and the plugin were always fine (`plugins\lama-cleaner.exe` answers `--help`, the
model is `plugins\lama-cleaner\models\big-lama.onnx`). What failed was the **lookup**: the runtime's
`prefs.plugIns` came back as defaults (`additionalPluginsFolder: ""`, `useAdditionalPluginsFolder:
false`) even though `%APPDATA%\Photocraft\config.toml` holds the right values, so the error was
"lama-cleaner.exe is not installed. Looked in: target\release\plugins\…, target\release\…".

Two things follow, and the second is **not settled**:

1. The helper lookup now walks the executable's ancestors for `plugins`, exactly as the model lookup
   already did (`crates/engine/src/cmd/retouch_cmds/lama_cleaner.rs`). Commit `f0b78a9178`.
2. **Why the running app does not adopt `[plugIns]` from `config.toml` is unexplained.** Measured with
   the control channel on a `--control` launch: `prefs.get` returned defaults for `plugIns`,
   `selectedTool`, `recentColors` and `groupTools`, while the file parsed cleanly with the real values
   (checked with a TOML parser). Every other preference behaved as if unread too. It may be that a
   `--control` launch uses a different store, or that the store fails to open for another reason. The
   next session should settle it: start the app normally, change one preference in the UI, and see
   whether `config.toml` keeps it — and whether `prefs.get` in that same run shows it.

## The build trap that caused a regression

A release build was started while `.cargo/config.toml` had **no** `[patch."https://github.com/storytold/craft-libs"]`
section — the state left behind by `cargo xtask craftlibs off`. Cargo then built the pinned upstream
`a6b9d9c9`, so the binary carried none of the fixes, and the Space bug came back. Nothing in the
build output said which craft-libs was in use.

`md/build-safety.md` now holds the gate: patch 211 crates, lock 8 lines, the checkout's commit, and the
log check (`Compiling craft (D:\…\craft-libs\crates\…)` means local; `(https://…?rev=…)` means the pin
— cancel and start over). `AGENTS.md` points at it.
